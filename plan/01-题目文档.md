> - **目标产出**：`10-16-2-mcp-tool-ops-lens`（纯本地 Python CLI，读本机 AI 编程工具会话日志与配置）

> - **定位宣言**："你往 agent 里加了十几个 MCP server，但哪个失败率最高？每次调用吃多少 token？哪个纯属拖慢 agent？——从本地会话日志统计每个工具的调用/失败/token 开销，给出可执行的删/换建议。管理侧工具已有很多，'可靠性+开销归因'侧近乎空白。"

## 一、介绍

AI 编程 agent（Claude Code、Codex 等）重度依赖 MCP server 与内置工具，但用户对"这些工具到底表现如何"几乎处于盲区：失败了没人统计，浪费了多少上下文 token 也没人数。典型痛点证据：

- ✅ HN《Show HN: Unclog – find and fix Claude Code context bloat》（id 47822779）作者原话："kept adding MCPs, skills, hooks... found I was **burning 16k tokens of context before typing a single message**"——MCP/工具的上下文开销被用户真实感知为痛点。
- ✅ HN《I Cut my Agent Tokens By 50%》（id 50047627）——token 开销优化是社区高频话题。
- ✅ BenjisCollector/agent-failure-study 自述实测："**91,747 production coding-agent tool calls: 4.12% hard failure rate, context budget overrun is the top mode**"——工具调用失败与上下文预算超支的痛点已被量化证实。

**开源空白**（基准日 2026-10-15，GitHub 检索式见 data/README.md，软论据⬜记检索式）：管理与同步侧已饱和（agent-deck 1085★、bridle 440★、claude-code-tool-manager 382★、mcp-linker 341★；清理侧 unclog 36★ 只做 bloat 清理不做失败率归因），而"可靠性+开销归因"侧最大仅 Harshit-J004/toolguard 15★，多条检索式命中为 0。**判定：近乎空白。**

## 二、任务要求（首期 5 个模块，其余留扩展）

### 模块 1：会话日志与配置解析
- **输入**：本机只读——`~/.claude.json`（mcpServers 按 project 分列、lastSessionMetrics、costUSD、inputTokens/outputTokens、usageCount、lastToolDuration）、会话 jsonl `~/.claude/projects/*/*.jsonl`（tool_use 含 `mcp__<server>__<tool>` 前缀命名、tool_result 成败、message.usage token 数）、`~/.claude/settings.json`（MCP 工具白名单）、`~/.claude/plugins/installed_plugins.json`、Codex `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`（session_meta / response_item / item_completed 含 token 数）。
- **输出**：统一内部 schema 的工具调用事件流（时间、server、tool、耗时、token、成败）。
- **引擎**：逐格式独立解析器，**带 schema 版本检测**（格式不识别时明确报错而非静默错解）。
- **确定性纪律**：⬜ 失败判定的精确字段语义（is_error 标志/异常文本模式）与跨版本格式漂移在 M1 数据先行阶段核对入库后，解析规则才允许进入计算路径；不承诺覆盖所有 agent 工具，首期只声明 Claude Code + Codex。

> **【M1 实测勘误，2026-10-16】** 本节原表述与实测不符之处已由 `data/README.md §五` 勘误，**原文保留不改、以勘误为准**：
> 1. 顶部数据源清单所称"`~/.claude/settings.json`（MCP 工具白名单）"——**实测 settings.json 无 `mcpServers` / `allowedTools` 键**；MCP 工具白名单实际在 **`permissions.allow`**。
> 2. "失败判定 = `is_error` 标志"——**实测 `is_error` 是三态**（`True`/`False`/**字段缺失，约占 50%**），缺失态不得默认为成功。
> 3. 另有新增边界：`settings.json` 的 `env` 块**含活体凭据**，已定为禁读键（见 plan/04 §二）。

### 模块 2：工具调用统计聚合
- **输入**：模块 1 事件流。
- **输出**：按 server / tool 两级维度聚合：调用数、失败数、重试数、平均耗时、单次 token 开销。
- **引擎**：确定性 SQL 风格聚合，无任何模型参与。
- **确定性纪律**：重试识别、耗时口径等与模块 1/3 共用的定义**一处定义**（见 data/README.md 数值口径纪律），多处引用不得手写第二份。

### 模块 3：失败模式归因
- **输入**：失败调用记录及其错误文本。
- **输出**：失败分类标签（超时 / 权限拒绝 / 参数错误 / 内容拒绝 / 其他）。
- **引擎**：规则匹配（模式表入库、可审计），非 AI 评分。
- **确定性纪律**：未在规则表中挂"已核对样例"的模式不得生效进入计算路径，落入"其他"。

### 模块 4：删换建议报告
- **输入**：模块 2/3 结果。
- **输出**：本地 HTML / Markdown 报告：失败率 Top、token 开销 Top、"建议移除"清单，每条建议附统计口径与样本量。
- **引擎**：阈值规则（阈值进配置文件可调，不写死在代码里）。
- **确定性纪律**：报告必须显示每条建议依据的口径与样本量，样本不足时明确降级为"数据不足"；建议≠自动修改。

### 模块 5：真值基准
- **输入**：合成会话日志（**程序化植入真值**：已知哪个 server 失败率多少、哪条应归为超时等）。
- **输出**：基准套件 + 对账报告（引擎输出 vs 植入真值）。
- **引擎**：合成生成器带真值标注，覆盖度口径按 server 维度（高/中/低失败率、正常/重试型 server）与失败模式维度（四类各至少覆盖）列最低覆盖项，写进 manifest。
- **确定性纪律**：合成日志只用假 server 名白名单（如 `mcp__fake-server__tool`），真实会话日志不入仓（见 .gitignore 与 data/README.md）。

**扩展项（不计入首期承诺）**：跨日趋势、预算告警、Cursor 等其他工具适配。

## 六、边界与非目标

- **不做 MCP 管理/安装/同步**：管理侧已饱和（agent-deck 1085★ 等），本题只做"可靠性+开销归因"。
- **不修改用户配置**：纯只读分析 + 建议；不自动删改任何 MCP server 配置。
- **隐私红线**：会话日志含 prompt 与代码，**纯本地运行，零上传、零遥测**；真实会话日志不入仓。
- **不做"AI 评分"**：所有统计是确定性计数，归因是规则匹配，不引入任何模型。
- **格式漂移风险**：不同工具版本日志格式会漂移，解析器需带 schema 版本检测；**不承诺覆盖所有 agent 工具，首期只声明 Claude Code + Codex**。
- **品牌隔离**：本方向另有姊妹仓库做"AI 代码重复/返工体检"（扫会话日志算返工指标）。本题聚焦 **MCP/工具调用的失败率与开销归因**，不同问题域；本仓库文档不提及姊妹项目。
- **首期范围限定**：仅上述 5 个模块，扩展项一律不承诺。
